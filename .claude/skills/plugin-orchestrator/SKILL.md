# Plugin orchestrator

Coordinates the plugin team to take a change from request (or a server follow-up issue) to a
verified draft PR, and prepares releases. It owns git and the GitHub issue that tracks the work;
the agents own editing and verification.

## Execution mode: subagent

An edit pass then a verification pass, looped at most twice. Agents run as subagents (`Agent`
tool) and hand off through files under `_agents_workspace/`. Agent-team tools are not used.

## Agents

| Agent | `subagent_type` | Role | Skill | Output |
| --- | --- | --- | --- | --- |
| plugin-editor | `plugin-editor` | Docs, skills, agents, evals, changelog, manifests | `plugin-change` | `_agents_workspace/03_plugin-editor_changes.md` |
| plugin-verifier | `plugin-verifier` | Checks, copy comparison, evals | `plugin-verify` | `_agents_workspace/04_plugin-verifier_report.md` |

Tools are referenced by role from `references/tools.md`.

## Workflow

### Phase 0: intake & triage (always first; this skill is the repo's entry point)

- **Answer directly and stop** — a question about the plugin ("which skill handles contact
  requests?"), a conversational message, something outside this repo, or a one-line obvious fix
  the user dictated. For the one-liner, make it, run `node scripts/check.mjs`, and report. No
  agents, no workspace, no issue.
- **A question about legislation itself** (a bill, a vote, a legislator) is the plugin's
  *product*, not work on the repo: answer it with the plugin's own skills
  (`get-legislation` and the slash commands), not this orchestrator's team.
- **In-domain work** — anything that will change `skills/`, `agents/`, `docs/`, `evals/`,
  `README.md`, `CHANGELOG.md`, `scripts/` or `.claude-plugin/`. Continue below.

| Request | Phases |
| --- | --- |
| Server follow-up, live-tools failure, tool docs drift | 0 (issue) → 1 → 2 → 3 → 4 |
| Skill or agent guidance, new command or agent, eval case | 1 → 2 → 3 (with evals) → 4 |
| Release | 5 |
| Review comments or CI failure on our PR | 2 (comments as findings) → 3 → push |

**Context check** (in-domain only), on `_agents_workspace/`:
- absent → initial run.
- present, and the request changes part of the last result → partial re-run of the affected
  agent, passing its prior output path.
- present, and the request is new work → move it to
  `_agents_workspace/archive/<YYYYMMDD_HHMMSS>/` and start fresh.

Keep the workspace out of git without touching `.gitignore`:

```bash
f=$(git rev-parse --git-path info/exclude); grep -qxF '_agents_workspace/' "$f" || echo '_agents_workspace/' >> "$f"
```

**Issue (GitHub Issues owns work state).**
1. List open issues: `mcp__github__list_issues` with `owner: cicada-guide`,
   `repo: plugin-anthropic`, `state: OPEN` (fallback: `gh issue list --repo
   cicada-guide/plugin-anthropic --state open --json number,title,body`). Titles starting
   `Docs follow-up:` come from the server orchestrator.
2. A `Docs follow-up:` issue is **ready** only when a comment on it says
   `Status: deployed and verified`. Read it with `mcp__github__issue_read` (`method:
   get_comments`). Not yet verified → tell the user it is waiting on the server deploy, and
   stop: documenting what the live server does not yet serve breaks the nightly check and every
   user who follows it.
3. For other work with no matching issue, create one (`mcp__github__issue_write`,
   `method: create`; fallback `gh issue create`), ending the body with the attribution footer
   `---\n_Generated by [Claude Code](https://claude.ai/code)_`.
4. Never rewrite an issue's human-written text.

### Phase 1: prepare

1. Save the request, issue number and route to `_agents_workspace/00_input.md` (`issue: #N`).
2. Save the live `tools/list` to `_agents_workspace/01_tools-list.json` (the command is in the
   `plugin-change` skill, section 1). If the issue names a server change, confirm the saved list
   shows it; if it does not, stop as in Phase 0 step 2.
3. Make sure you are on the session's designated branch (never `main`).

### Phase 2: edit

```text
Agent(subagent_type: "plugin-editor", description: "Edit plugin docs",
      prompt: "Issue #N. Task: <brief, including the server change from the issue body>.
               Live list: _agents_workspace/01_tools-list.json. Prior findings:
               _agents_workspace/04_plugin-verifier_report.md (if a fix loop). Follow the
               plugin-change skill; write _agents_workspace/03_plugin-editor_changes.md.")
```

### Phase 3: verify (producer–reviewer loop)

```text
Agent(subagent_type: "plugin-verifier", description: "Verify plugin change",
      prompt: "Issue #N. Read _agents_workspace/03_plugin-editor_changes.md and the diff.
               Evals: <run the cases for the changed entry points | not needed>. Follow the
               plugin-verify skill; write _agents_workspace/04_plugin-verifier_report.md.")
```

- `VERDICT: PASS` → Phase 4. `VERDICT: FAIL` → Phase 2 with the report; at most two loops, then
  stop and show the user the open findings.
- Evals cost model calls on the maintainer's account. Ask before a full-suite run; run the
  changed entry points' cases by default.

### Phase 4: integrate

1. Read the changes file and the report; check the diff matches.
2. Run `node scripts/check.mjs` yourself once more.
3. Commit on the designated branch (plain sentence-case subject, the session's attribution
   lines), push with `git push -u origin <branch>`, and open a **draft** PR with `Closes #N`.
   For a server follow-up, link the server PR. Subscribe to its activity.
4. Summarize: what changed, what was verified (`ran` / `not run`), the PR link. Merging is the
   user's decision; never merge.

### Phase 5: release (on request, after the docs PRs are merged)

Follow `PUBLISHING.md`, "Before each release", in order: reconcile against the live server,
bump all three version fields together, date the changelog and its compare links, confirm
`/health`, land on `main`. The tag is pushed by `tag-release.yml`; check its run after merge
and report the tag. Run plugin-verifier on the release diff before the PR.

## Error handling

| Situation | Strategy |
| --- | --- |
| An agent fails or returns nothing | retry once; on a second failure, continue without it and say so |
| Verifier FAIL twice | stop and hand the findings to the user |
| Live server unreachable | check `/health`; verify against a saved list only if it was saved after the deploy was confirmed; otherwise stop |
| Follow-up issue not yet released | tell the user it waits on the server deploy; do nothing else |
| GitHub MCP refuses | fall back to `gh`; if neither works, tell the user what to file and continue |
| `claude plugin eval` unavailable | mark `not run` in the report and give the user the command |

## Test scenarios

- **Normal:** a `Docs follow-up: search_people gains chamber` issue with a
  `Status: deployed and verified` comment → live list saved and shows `chamber` → editor
  updates the three tool lists, the parameter table, the changelog → verifier: `check.mjs`
  and `check-live-tools.mjs` pass, copies agree, no skill guidance changed so evals are
  skipped → PASS → draft PR with `Closes #N` and the server PR link.
- **Error:** the same issue without the deploy comment → the orchestrator reports it is waiting
  on the server and stops; nothing is edited.
- **Triage:** "how do I run the evals?" → answered from `docs/howto-verify-a-change.md`; no
  agents.
